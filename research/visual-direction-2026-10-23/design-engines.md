## APIs : ne pas confondre transport et génération

- **v0 MCP** expose création et suivi de chats, messages, reprise de tâches et URL de prévisualisation. La connexion initiale nécessite OAuth ; il ne faut pas placer une clé API dans sa configuration MCP. Le SDK v0, lui, utilise une clé côté serveur. Le guide MCP signale encore la v2 comme bêta. [Guide officiel](https://v0.app/docs/api/v2/guides/mcp-server), [SDK](https://v0.app/docs/api/v2/quickstart).
- **Stitch** dispose du SDK `@google/stitch-sdk` et du serveur `https://stitch.googleapis.com/mcp`. Les méthodes documentées génèrent un écran ou des variantes et récupèrent HTML/capture. L’authentification requiert une clé ou un jeton OAuth avec projet ; le SDK ne procure pas ces droits. [Dépôt officiel](https://github.com/google-labs-code/stitch-sdk).
- **Figma REST** sert notamment à lire des fichiers/calques, gérer variables et événements ; ce n’est pas une API publique de prompt vers Figma Make. Le **MCP Figma** ajoute contexte de design et écriture native sur le canevas. Sa documentation mentionne aussi la récupération des ressources d’un fichier Make, ce qui reste distinct d’un lancement de génération Make. [REST](https://developers.figma.com/docs/rest-api/), [MCP](https://developers.figma.com/docs/figma-mcp-server/).
- **Flowith** affiche une API personnalisée à venir. Sa règle d’usage interdit l’automatisation non autorisée de nœuds à grande échelle ; on ne doit donc pas remplacer une API absente par des scripts supposés illimités. [Page officielle](https://flowith.io/pricing/).

## Moteur, skill et galerie

Un **modèle** calcule une sortie ; une **application de design** fournit canevas, variantes, aperçu et outils d’édition ; un **skill** organise le travail de l’agent qui le lit ; une **galerie** fournit des références visuelles. Ajouter Impeccable ou Frontend Design ne transforme pas le modèle sous-jacent en Opus. Une image Pinterest ou une collection de sites ne génère pas non plus le code et ne donne pas automatiquement des droits sur ses images.

## Décision V17 et vérifications restantes

V17 adapte la variante A : photographies dominantes, titres sous les images, recherche à la jonction du visuel d’accueil et du contenu. Les fonds de lecture clairs et la sidebar existante sont conservés. Les dimensions proposées par le modèle ont été recalculées selon l’espace réel laissé par la navigation. La recherche du catalogue reste dans le flux pour éviter de réintroduire les recouvrements mobiles déjà observés.

Flowith précise dans sa réponse ne pas avoir ouvert les références visuelles citées : sa proposition n’est ni une preuve de visite de ces sites ni un résultat de test. Les étapes suivantes restent pertinentes pour évaluer l’implémentation :

1. Garder la version précédente à grandes images comme référence préférée, et les corrections d’interaction utiles comme contraintes : recherche lisible, sources claires, lecteur partagé et aucun recouvrement mobile.
2. Produire **deux variantes du même écran**, avec les mêmes photographies autorisées et vrais titres : une version éditoriale photographique et une version galerie d’apprentissage. Montrer chacune à 390 px et en desktop, avant d’étendre le style.
3. Évaluer les écrans avec des critères observables : place des images, lecture du titre, visibilité des commandes, accès aux références, distinction vidéo/guide et fluidité du défilement. Ne pas choisir sur le nom du modèle ou le nombre d’étoiles d’un skill.
4. Intégrer la variante retenue dans le frontend existant. La recherche, les 36 901 vidéos et les sources documentaires n’ont pas besoin de changer pour comparer une direction visuelle.
